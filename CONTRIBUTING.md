# Правила внесения изменений

Любое изменение — написанное человеком, коллегой или сгенерированное
инструментом автоматической генерации кода — считается потенциально
ошибочным и обязано пройти один и тот же путь проверки, прежде чем
попасть в основную ветку и релиз:

```
задача → изменение кода → локальные проверки → Git → CI → образ → CD → проверка релиза → наблюдение
```

Ни один способ создания кода (вручную, парой, ассистентом) не освобождает
изменение от обязательных проверок ниже.

## 1. Порядок работы над функцией
1. Завести задачу (issue) с коротким описанием и критериями приёмки.
2. Создать ветку от `main`: `feature/<кратко-суть>` (например,
   `feature/attendance-stats-endpoint`).
3. Вносить изменения небольшими, осмысленными коммитами
   (`git commit -m "add X"`, `git commit -m "test X"`, `git commit -m "docs: X"`).
4. Перед каждым push и перед созданием запроса на слияние — обязательно
   выполнить `make verify`.
5. Открыть запрос на слияние (Pull Request) в `main` со ссылкой на задачу,
   описанием изменения и результатом `make verify`.
6. После проверки (CI + ревью) — слияние в `main`, удаление ветки.
7. Значимые версии отмечаются тегом (`git tag vX.Y.Z`).

## 2. Обязательные локальные команды перед PR
```
make quality   # ruff + black --check
make test      # pytest
make verify    # quality + test одной командой — обязателен перед PR
```
Запрос на слияние без прошедшего `make verify` не принимается.

## 3. Запрещённые действия
- Удалять или произвольно пропускать («skip») существующие тесты, чтобы
  «протолкнуть» изменение.
- Отключать анализаторы (ruff/black) точечными комментариями без явного
  обоснования в PR.
- Снижать пороги качества / ослаблять шаги CI ради прохождения проверки.
- Коммитить файл `.env`, реальные секреты, локальные базы (`*.db`) —
  они входят в `.gitignore` и не должны попадать в репозиторий ни при
  каких обстоятельствах.
- Прямой push в `main`, минуя ветку и запрос на слияние.
- Слияние PR с конфликтами, оставленными в коде (маркеры `<<<<<<<`).

## 4. Критические файлы приёмки
Изменения следующих файлов обязательно должны быть явно видны в diff
запроса на слияние и проверяться отдельно, даже если PR посвящён другой
задаче:
- `Makefile`, `.gitignore`, `.env.example`
- `alembic/versions/*` (миграции схемы БД)
- `docs/DATA_MODEL.md`, `docs/API.md`, `docs/TZ.md`
- `Dockerfile`, `docker-compose.yml`

## 5. Порядок приёмки (Definition of Done)
Функция считается принятой, если одновременно верно:
1. Есть задача, ветка и минимум 2–3 осмысленных коммита с понятными
   сообщениями.
2. `make verify` проходит локально без предупреждений об отключённых
   проверках.
3. Реализовано минимум одно содержательное бизнес-правило или явно
   указано, что в этой задаче правило не менялось.
4. Обновлена документация (`docs/API.md` и/или `docs/DATA_MODEL.md`), если
   менялся контракт API или схема данных.
5. PR прошёл слияние в `main` без потерянных изменений (конфликты
   разрешены осознанно, а не «принять чужую сторону не глядя»).
6. Автор способен на защите объяснить каждую строчку diff, назначение
   каждого изменённого файла и то, зачем нужна каждая проверка.

## 6. Ветвление и версии
- `main` — всегда рабочая, покрытая тестами ветка.
- `feature/*` — одна функция = одна ветка.
- Теги версий — семантическое версионирование `vMAJOR.MINOR.PATCH`
  (первая версия: `v0.1.0`).
