# Техническое задание — «Городская Дума»

## 1. Назначение системы
Система предназначена для учёта депутатов городской думы, комиссий, их
председателей, заседаний и посещаемости депутатами заседаний. Используется
аппаратом думы для ведения актуального реестра и подготовки отчётов по
посещаемости за период.

## 2. Категории пользователей
| Роль | Возможности |
|---|---|
| Секретарь думы / администратор | Полный доступ: ведение депутатов, комиссий, состава, заседаний, отметка посещаемости |
| Сотрудник аппарата комиссии | Работа с заседаниями и посещаемостью «своей» комиссии |
| Наблюдатель / депутат | Только чтение: списки, статусы заседаний, отчёты по посещаемости |

В ЛР1 система не содержит аутентификации/авторизации (будет добавлено в
последующих лабораторных); API открыт, но структурирован так, чтобы роли
можно было наложить позже без изменения модели данных.

## 3. Основные сценарии использования
1. Секретарь регистрирует депутата и включает его в состав комиссии.
2. Секретарь назначает председателя комиссии.
3. Секретарь создаёт заседание комиссии с датой и повесткой.
4. По итогам заседания отмечается посещаемость каждого приглашённого депутата.
5. Заседание переводится в статус «проведено» — при этом проверяется кворум.
6. Формируется отчёт по посещаемости конкретного депутата за период (агрегат).

## 4. Обязательные правила работы (бизнес-правила)
- **Один председатель на комиссию.** У комиссии не может быть более одного
  депутата с флагом `is_chair = true` одновременно. Попытка назначить
  второго председателя без снятия первого — ошибка `409 Conflict`.
- **Кворум.** Заседание комиссии нельзя перевести в статус `held`
  (проведено), если число депутатов со статусом посещаемости `present`
  не превышает половины списочного состава комиссии. Правило не
  применяется к пленарным заседаниям (`commission_id = null`).
- **Уникальность членства.** Один депутат не может быть дважды включён в
  одну и ту же комиссию (уникальная пара `commission_id + deputy_id`).
- **Уникальность отметки посещаемости.** На одном заседании у одного
  депутата может быть только одна отметка посещаемости (уникальная пара
  `meeting_id + deputy_id`).

## 5. Сущности и связи
См. [`docs/DATA_MODEL.md`](DATA_MODEL.md) — ER-диаграмма и описание полей.

Кратко:
- `Deputy` (депутат) 1—N `CommissionMembership` N—1 `Commission` (комиссия) —
  связь многие-ко-многим через таблицу членства с признаком председателя.
- `Commission` 1—N `Meeting` (заседание комиссии); пленарные заседания думы
  имеют `commission_id = NULL`.
- `Meeting` 1—N `Attendance` (посещаемость) N—1 `Deputy`.

## 6. Ограничения
- Имя депутата — от 2 до 255 символов, обязательно.
- Название комиссии — уникально в рамках системы.
- Статус заседания — одно из значений: `scheduled`, `held`, `cancelled`.
- Статус посещаемости — одно из значений: `present`, `absent`, `excused`.
- Удаление депутата или комиссии каскадно удаляет связанные членства,
  заседания (для комиссии) и отметки посещаемости.

## 7. Обработка ошибок
| Код | Ситуация |
|---|---|
| 404 | Депутат/комиссия/заседание с указанным id не найдены |
| 409 | Нарушение бизнес-правила: второй председатель, дублирующее членство, дублирующая посещаемость, отсутствие кворума |
| 422 | Некорректное тело запроса (нарушение схемы/типов/ограничений длины) |

Формат ошибки единый: `{"detail": "человекочитаемое описание"}`
(для 422 дополнительно передаётся массив `errors` с деталями валидации).

## 8. Требования к хранению данных
- Реляционная СУБД. В ЛР1 — SQLite (файл `duma.db`) для минимальной
  конфигурации без внешних зависимостей; строка подключения задаётся через
  `DATABASE_URL` и без изменения кода может указывать на PostgreSQL
  (используется в последующих лабораторных, см. `docker-compose.yml`).
- Схема управляется миграциями Alembic (`alembic/versions`), применяются
  командой `make migrate`.
- Резервное копирование/восстановление — `make backup` / `make restore`
  (копия файла БД в `backups/`, каталог не хранится в Git).
