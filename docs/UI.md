# Веб-интерфейс — «Городская Дума»

Лёгкий статический дашборд поверх HTTP API — не отдельное приложение,
а просто удобный способ посмотреть и внести данные без curl/Swagger.
Реализован одним файлом (`static/index.html`) на чистом HTML/CSS/JS,
без сборки и фреймворков; обращается к тому же самому API, что описано
в [`API.md`](API.md) — никаких отдельных «UI-эндпоинтов» не заводилось.

Открывается по адресу `http://localhost:8000/` (автоматически
перенаправляет на `/ui/`, где физически отдаётся сам файл).

## Навигация (левое меню)

| Раздел | Адрес (hash-роут) | Что показывает |
|---|---|---|
| Главная | `#/` | Сводные счётчики: количество депутатов, комиссий, заседаний |
| Депутаты | `#/deputies` | Список депутатов, форма добавления, статистика посещаемости по каждому |
| Комиссии | `#/commissions` | Список комиссий, форма создания |
| Комиссия (детали) | `#/commissions/{id}` | Состав комиссии (с пометкой председателя), заседания комиссии, формы добавления члена и заседания, кнопка «Провести» |
| Посещаемость | `#/attendance` | Выбор заседания из списка, отметки посещаемости, форма добавления новой отметки |

Переключение между разделами происходит без перезагрузки страницы —
через `location.hash` и небольшой самописный роутер (без библиотек).

## Какие эндпоинты API использует каждый раздел

- **Главная** — `GET /deputies`, `GET /commissions`, `GET /meetings` (берётся только длина списков).
- **Депутаты** — `GET /deputies`, `POST /deputies`, `GET /deputies/{id}/attendance-stats`.
- **Комиссии (список)** — `GET /commissions`, `POST /commissions`.
- **Комиссия (детали)** — `GET /commissions/{id}`, `GET /commissions/{id}/members`,
  `GET /meetings?commission_id=`, `GET /deputies` (для подписи имён),
  `POST /commissions/{id}/members`, `POST /meetings`,
  `PATCH /meetings/{id}/status` (кнопка «Провести» — здесь же виден
  реальный текст ошибки кворума, если правило не выполнено).
- **Посещаемость** — `GET /meetings`, `GET /meetings/{id}/attendance`,
  `GET /deputies`, `POST /meetings/{id}/attendance`.

## Как показаны ошибки бизнес-правил

Любой неуспешный ответ API (`404`/`409`/`422`) перехватывается в общей
функции `api()` внутри `static/index.html` и выводится как баннер с
текстом из поля `detail` — тем же самым, что генерирует `crud.py`.
Отдельной логики валидации на стороне интерфейса нет: вся проверка
бизнес-правил (единственный председатель, кворум, уникальность
членства/посещаемости) выполняется на сервере, интерфейс лишь честно
показывает то, что вернуло API.

## Ограничения (осознанно не реализовано)

- Нет удаления комиссий/заседаний/членства — только просмотр и добавление
  (API это умеет, интерфейс — нет; не требовалось критериями задачи).
- Нет авторизации и ролей — как и в самом API на этом этапе.
- Не адаптирован под мобильные экраны отдельно — минимально читаем на
  узких экранах за счёт простой раскладки, но не оптимизирован специально.
